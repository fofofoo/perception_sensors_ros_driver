# README 模板：基于协议开发的 ROS 消息节点

本模板用于「某个硬件设备 + 某套通讯协议 → 一个或多个 ROS 消息节点」这类项目。
写法来自 `ultrasonic_radar_demo` 仓库的三份 README，可直接复制后替换占位符。

使用方式：

- 功能包 README 用第二部分（骨架 A），必写；
- 仓库总 README 用第三部分（骨架 B），多协议/多接入方式时写；
- 提交前过一遍第四部分的自检清单。

占位符统一写成 `<尖括号中文>`，替换后删除尖括号。

---

## 一、文档分层

| 层级 | 读者 | 内容重心 |
| --- | --- | --- |
| 仓库 README | 第一次接触设备的人 | 设备是什么、有几种接法、协议长什么样、踩过哪些坑 |
| 功能包 README | 要跑/要改节点的人 | 话题语义、参数、编译运行、实现边界 |
| 旧包/子模块 README | 要评估旧代码的人 | 已实现的最小事实 + 已知缺陷 |

- 包 README 不复述协议全文，只留一句关键约束，细节链回仓库 README；
- 仓库 README 不复述节点实现，链回包 README；
- **互相引用，不互相抄。**

## 四、写作原则

1. **拓扑图先行**：每节开头给一屏 ASCII 链路图，标注地址、端口、从机号。
2. **报文逐字节标注**：不只写「发送读请求」，要把每个字段指出来，并换算成人能理解的量。
3. **一切常量表格化**：寄存器、端口映射、控制字、参数、探头映射、模式对比。
   正文只写「为什么」和「注意事项」，不复述表格。
4. **三档常量分开讲**：
   - 协议固定值（寄存器地址、从机号）；
   - 现场可调值（IP、端口、周期、超时）；
   - 代码写死值（话题名、阈值）。
   混在一起是这类 README 最常见的失败。
5. **数据语义单独成段**：单位、编码、无效值、无回波含义。反直觉事实必须明写
   （「读到 0 不是通讯故障」）。
6. **陷阱写成「现象 → 原因 → 解决」**，不要只写结论。
7. **实测经验值写明依据**，否则后人会去「优化」回错误值。
8. **保留未采用的方案**，标注「历史方案，未采用」，防止重走弯路。
9. **已知缺陷用表格**，列「位置 / 问题」，并写清影响（越界读、忙等占 CPU）。
10. **链接全部用仓库相对路径**，源码、msg、doc 都要能点开。
11. **三层频率必须交代清楚**：不能只写「发布频率 xx Hz」，要分别写清
    ① 硬件发出/上报频率（由转速、采样周期、输出速率寄存器等什么决定，默认值与单位，现场怎么改）；
    ② 软件轮询/采集频率（回调驱动还是定时轮询，与数据到达频率的倍数关系，轮询间隔不等于话题频率）；
    ③ 话题/消息发布频率（逐帧回调、定时器还是主循环轮询，与上游频率的对应关系，是否被主循环或队列截断）。
    同时给出频率传递图、启动填充时间、频率上限与丢帧/覆盖规则、多帧累加造成的数据量放大倍数、
    每个频率参数的位置及修改后的连带影响。频率必须回源码与设备手册核实，不能凭印象填写。
